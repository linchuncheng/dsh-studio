# 产品定义：从需求提出到交付，做到 AI Native

> 定稿日期 2026-11-18。来源：七位专家会诊（CTO / 产品经理 / 前端开发者 / 后端架构师 /
> 自动化优化架构师 / 工程效率工程师 / Git 工作流工程师），由主会话合并去重后成文。
> 本文是**范围与验收**的唯一出处；实现细节看 `AGENTS.md`，界面约定看 `docs/ui.md`。

## 0. 一句话判断

**当前是 AI Assisted Delivery，不是 AI Native。**

AI 是执行手，判定权在确定性规则和人手里。要变成 AI Native，缺的不是更多 agent，
而是三件事：**把判定交给 AI、把交接变成契约、把失败变成数据**。

判断依据（均为代码事实，非估计）：

- 用例生成是字符串模板：一条验收条件 = 一个用例标题，没有验收条件就给一条「主流程」。
  **所以"用例全绿"不代表验过。**
- 需求门禁只检查"卡上有没有产品/架构的评论"，**不检查评论说了什么**——一句"已澄清"就能过。
- `studio_task_signoff` 默认 `by='人'`，`requirement_signoff` 默认 `by='agent'`：
  同一套门禁，两个默认值相反。AI 可以在某些路径上替人签字。
- 代码评审 `action=review` 缺省回落成 `approved`（可以自评）。
- 发版审批不在 `releaseGate` 的 blocker 里（审批不是门禁）。

## 1. 目标用户

| 角色 | 规模 | 核心痛点 | 该被 AI 补上的判断 |
| --- | --- | --- | --- |
| **P1 团队负责人 / 产品** | 1 | 需求没写完就开工；"做完了"没有判定标准 | 需求是否够清楚、功能点切得对不对 |
| **P3 研发**（真正高频） | 2–3 | 上下文太长对不上号；自报执行记录没人核 | 方案是否覆盖功能点、代码与描述是否一致 |
| P4 测试（常由研发兼） | 0–1 | 用例不可重跑；"通过"是嘴说的 | 用例是否真覆盖验收条件 |
| P5 业务提出方 | 5–20 偶发 | 提了不知道去哪了 | 提单是否可被拆解 |

四个角色 + 一组 AI 专家（产品/架构/研发/测试）。**单团队、单实例、单进程**是明确前提；
不做多租户。

## 3. V1 范围：冻结功能面，只补三件事

加功能的速度已经超过验证的速度（10 天 40+ 个版本）。**V1 不加任何新页面。**

### 必做

| # | 内容 | 对应的已证实缺口 |
| --- | --- | --- |
| 1 | **单写者 + 写入 CAS**：用现成 `locks` 表做单写者；task 加 version，不匹配返回 409 | 两个进程同时写，后写覆盖先写，**静默丢卡且无日志** |
| 2 | **attempts + 租约 + recover**：重启把过期 running 标 `abandoned`，**同时清掉 dispatch 标记** | 崩溃后卡永久停摆（`tick` 见 `dispatch.status === status` 就永远跳过） |
| 3 | **假重试修复**：`/task/agent/retry` 同时清 `task.dispatch` | 按钮提示"下一轮自动接手"，实际永不重派 |
| 4 | **用例生成 LLM 化**：按正/反/边界三路径，**每条必须带可执行断言**（http/shell）；带不出断言的标 draft 且不计入覆盖 | 模板用例 → 门禁强度虚高 |
| 5 | **交接契约**：卡片增加结构化字段（决策 / 假设 / 未决 / 风险 / 影响面），提示词先读契约再看评论尾 6 条 | 换专家/换会话只能靠猜 |
| 6 | **事件账本落库**：`(需求, actor, action)` 写入 side 键，用来算人工介入率 | **今天算不出来**，无法向任何人证明 ROI |
| 7 | **前端零体积项**：`dispatchPhase()` 纯函数（运行中/已停滞/排队中三态）+ 1.5 秒轻轮询 `/agents` + 复用 `details` 做运行托盘 | 前端预算只剩 23 kB（1437 / 1460） |

### 暂缓（明确不做，附理由）

| 不做 | 理由 |
| --- | --- |
| 自动签字 / 自动关缺陷 / 自动发布 | 签字是责任转移。**没有可信判定的自动签字 = 把门禁变成装饰。** 这一条 CTO 行使否决权 |
| 新增前端页面（时间线、矩阵大图、新视图） | 体积只剩 23 kB，加 UI 前先还技术债 |
| 专家从 4 位扩到 8+ 位 | 会话是贵的（token + 并发上限 2）。现在是"判定弱"，不是"人不够" |
| 向量库 / RAG | 现有知识量（技能库 + 每团 ≤20 条记忆）用不上检索。先做结构化失败回流 |
| 多模型路由 / 自动选模型 | 没有评测集就无法比较，等于在噪声上做决策 |
| Redis / 消息队列 / 微服务 | 单进程 + 5 秒 tick 今天够用，没有任何指标显示这里是瓶颈 |
| 全量 Event Sourcing 改造 | config 继续留 blob，只把任务生命周期拆成可查询的行 |
| 多租户 / 权限体系重做 | 与本次目标无关 |

## 4. 可观察验收标准

**原则：每条都能断言，不靠感觉。**「已实测」列是当前状态。

| # | 能力 | 断言 | 今天 |
| --- | --- | --- | --- |
| 1 | 崩溃自愈 | `kill -9` 后重启，≤2 tick 内重派**恰好 1 次**；events 出现 `abandoned` + `dispatched` | ❌ 永久停摆 |
| 2 | 停摆可测 | `dispatch.status===status && state!=='running'` 持续超过 2 tick 的卡数 **= 0** | 必然 ≥1 |
| 3 | 写不丢 | 两进程各建一卡 → 重启后两张都在，或第二实例启动即被拒 | ❌ 只剩一张 |
| 4 | 失败不留半截 | 注入 persist 失败后，内存态 == 磁盘态 | ✅ 已做（`store.mutate` 落盘失败回滚内存，`tests/store-cas.test.mjs` 覆盖） |
| 5 | 入站幂等 | 同 `Idempotency-Key` 连发 2 次评论 → 评论数 = 1 | ✅ 已做（0.6.0：POST 带 `Idempotency-Key`，同 key 回放第一次的响应并标 `x-idempotent-replay`；24h TTL、上限 200 条，存在 side 键不涨 revision） |
| 6 | 冲突可见 | 两人带同一 version 改同一卡 → 一方 200、一方 **409 且返回当前卡** | ✅ 已做（0.6.0：卡有 `version`，`/task/update` 带 `ifVersion` 时后写方得 409 + 当前卡；不带 `ifVersion` 保持老行为） |
| 7 | 无幻影事件 | webhook 收到的每个 seq 都能在 events 查到 | ✅ 已做（0.7.0：事件先写进账本拿到 seq 再投递，落账失败就**不投**；`GET /studio-api/events?since=` 可按 seq 查，保留最近 500 条） |
| 8 | **用例覆盖强度** | 带可执行断言的用例 ÷ 全部 ≥ **60%** | ≈ 0 |
| 9 | 门禁一次通过率 | 40–70%（<30% 说明上游澄清失效，>90% 说明门禁太松） | ✅ 已测量（0.8.0：到过「待验收」的卡里，第一次进待验收就直接完成的比例；效能页 KPI + 被打回的卡清单） |
| 10 | 派单周活 | 有 ≥1 条专家评论的卡 / 周 ≥ 15 张 | ✅ 已测量（0.8.0：按 ISO 周分桶，只数带 AI 评论的卡；效能页给近 8 周序列 + 是否达标） |
| 11 | AI 不可代签 | AI 会话调用签字接口 → 被拒，或标 `by=agent` 且**不满足人工签字条件** | ✅ 已做（0.3.9：工具签的字记 `agent`，准出直接拦；老记录按专家名册识别） |
| 12 | 真机事实对账 | 真实 GitLab 令牌下 `verify-gitlab-facts` 7/7 | 仅 mock 验过 |
| 13 | 自动化率 | 「无人工介入走完 澄清→派单→用例→准出」的需求占比（目标见 §6） | **已测量**（0.5.1 起效能页有；口径与验收签字一致，角色名记「来源不明」不冒充人工介入） |
| 14 | 平均交付时长 | 需求创建 → 发布的中位数（按需求，不按卡） | ✅ 已测量（0.8.0：需求创建 → **验收签字**的间隔，取中位数；「发布」这一步还没有可靠时间戳，所以用签字时间代替，口径写在 `src/host/delivery.js` 里） |

## 5. 落地顺序

**第一批（止血，3–5 天）**：① 单写者 + CAS ② 崩溃自愈（attempts + 清理 dispatch 标记）
③ 假重试修复 ④ `dispatchPhase` 三态 + 1.5s 轻轮询

**第二批（治假绿 + 可观测，1–2 周）**：⑤ 用例生成 LLM 化 ⑥ 交接契约 ⑦ 事件账本
⑧ 运行托盘 / 待我处理收件箱

**第三批（证明，2–3 周）**：⑨ 门禁身份校验（AI 不可代签）⑩ 质量看板六块
⑪ 真实 GitLab 接入 ⑫ AI vs 人工对照组

每批独立可发布。**每批发版前必须过 `npm run release:preflight`**（文档 + 真机三套探针）。

## 5.1 用例生成的正确形态（2026-11-19 实测后的结论）

### 试过并证伪的

1. **模板生成**（一条验收条件 = 一个用例标题）→ 全库 101 条用例、**0 条可执行**。
   根因是 `addDraftCases` 里把 `http` 硬编码成 `null`（已修），但修完仍不够。
2. **规则推断**（条件里有 URL 就生成接口用例）→ 在真实验收条件上无效。
   实测卡 `t-52a15ac7`：条件是「错误密码返回 401」，这是**语义**不是**地址**，
   规则推不出 `POST /login`，两条新用例仍是草稿。

### 平台约束（决定形态）

仓库里唯一的模型入口是 `ctx.agents.create` —— **没有一次性问答 API**。
所以不能做成点一下按钮、后台调一次模型。

### 定下来的做法

用例生成走**派单**，由测试专家在会话里产出，通过工具落库：

| 环节 | 谁做 | 落点 |
| --- | --- | --- |
| 生成断言 | 测试专家会话 | 提示词要求输出结构化 JSON：`{method, path, body, expectStatus, expectContains}` |
| 落库 | 新工具 `studio_task_add_cases` | 校验 schema、拼 `baseUrl + path`、写进 `task.cases` |
| **当场验证** | 同一工具内 | **生成后立即试跑一条**；跑不通就不算生成成功，回报给专家重写 |

第三条是关键：让生成的用例跑不了当场暴露，而不是攒成一百条草稿。
尺子已经有了（`src/host/case-strength.js` 的 `coverageStrength` / `meetsCoverageTarget`），
用它守住新增用例必须可执行。

### 落地进度

| # | 做什么 | 状态 |
| --- | --- | --- |
| 1 | `prompt-ab.mjs --setup-only` 确认派单通路可用（免费） | ✅ 2026-11-19，建/删专家通路可用、零 token |
| 2 | `studio_task_add_cases`：校验 schema、拼 `baseUrl`、**当场试跑一条** | ✅ 2026-11-19，`src/host/executor.js` 的 `addAssertedCases`；不合法整体拒绝（一条都不写），试跑不通过如实标 `fail` 并把原因回给专家；9 条单测在 `tests/case-intake.test.mjs` |
| 3 | 测试角色提示词追加「用例必须带可执行断言」 | ✅ 2026-11-19，`buildExpertPrompt` 的 `test` 分支 |
| 4 | 真派一次单，断言新增用例的 `coverageStrength.executable > 0` | ✅ 2026-11-19，见下（**顺带暴露一个真 bug**） |

### 存量：无断言的用例（2026-11-19 普查）

| 卡 | 列 | 可执行 / 无断言 |
| --- | --- | --- |
| `t-a55ccbfc` REQ-001 退款流水拉取 | 待验收 | 1 / 13 |
| `t-d09553cf` REQ-002 对账差异比对 | 开发中 | 0 / 12 |
| `t-4ba0a476` REQ-002 并发扣减压测 | 已完成 | 0 / 6 |
| `t-e42bd8b4` BUG-001 并发不超卖 | 待验收 | 1 / 3 |
| `t-a5939564` REQ-002 导出进度展示 | 待开发 | 6 / 3 |

处理原则：**不做批量「一键补断言」**（规则推断那条路已经在 §5.1 开头证伪）。靠两条腿走——
① 卡推进到验收前，接单专家被要求补（提示词点名，不看列）；② 用例库能筛「只看无断言」，人一眼知道还差多少。
已完成卡上的空壳留着当历史记录，不为凑数字去改。

### 第 4 步的判据

不是「跑完了」就算过，要同时满足三条：

1. 卡上新增用例的 `http`/`shell` 不为空（`coverageStrength.executable > 0`）；
2. 专家**收到过**试跑结果（通过或失败都行，但必须是被工具返回的，不是它自己编的）；
3. 只有标题没有断言的新用例数 = 0。

### 第 4 步的实测（2026-11-19，真机 192.168.120.218）

派单：`POST /studio-api/agents/run {id: t-52a15ac7, expert: 测试工程师}`，卡是「REQ-004 登录失败次数限制与锁定」。

| 判据 | 结果 |
| --- | --- |
| 可执行用例 | **11 条全部可执行**（10 条接口 + 1 条 shell 独立探针），空壳 0 条 |
| 专家收到试跑结果 | 是：`studio_task_add_cases` 真的被调用（会话日志 `tool/call` seq 439），第一条当场返回 200/38ms |
| 标题型用例 | 0 条 |
| 回归 | 用例真打 `http://127.0.0.1:8787/api/auth/login`：200 / 401 / 423 / 403 四类状态码都验到了 |

**它还替我抓到一个真 bug**：shell 用例写的是 `expectExitCode`，执行器读的是 `expectExit`，
于是命令退出码 0 也被判「退出码 0（期望 undefined）」，平台还据此自动开了一张缺陷卡——
测试专家核对后把它关掉并标了「误报：平台字段名不一致，不是产品缺陷」。
这一条在 0.3.6 修掉了：统一 `expectExit`，且**写库前先过 `sanitizeCase`**，让「刚写入的形状」与「重启后加载的形状」一致。

> 结论：用例生成这条路走通了。**尺子是真的**——11 条用例能跑，
> 而且第一次真派单就证明这套校验能反过来查出平台自己的问题。

## 7. 与会诊结论的差异（本稿做的裁定）

1. **前端要不要加"运行托盘中转站"**：前端提议加，CTO 说预算只剩 23 kB。
   裁定：**只做零体积实现**（复用 `details` + 纯函数 + 轻轮询），不做新页面。
2. **后端要不要做全量 Event Sourcing**：裁定 **不做**，只把任务生命周期拆成可查询的行，
   config 继续留 blob——避免一次大改换不来可观测收益。
3. **产品经理的 V1（真实链路跑通）与 CTO 的 V1（补判定与交接）**：合并——
   跑通是目的，补判定与交接是唯一手段，二者不冲突。
4. **工程效率的"AI 质量看板"**：放到第三批。没有第一二批产生的真实失败样本，
   看板只能给第 0 天的数据打分。
